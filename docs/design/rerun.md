# 多轮重跑(复审)

> 返回 [文档索引](../README.md)

作者按意见改了代码、在 PR 上回了话之后,reviewer 需要**再跑一轮**:确认上一轮提的问题改没改、新改动有没有引入新问题,同时**不要再看一遍已经被自己剔除的东西**。

所以重跑不是「重新扫描一次」,而是「**带着上一轮的结论和 reviewer 的判断,再审一次**」。一次 review = **N 轮**(round),首轮与每次重跑各占一轮,轮次号只增不退,失败的轮次也留在履历里。

## 每轮新开一个 codex thread

复审**不复用**上一轮的会话,而是起一个干净 thread,把上一轮的上下文用**结构化 prompt** 注入。

理由是行号:复用会话意味着新旧两份 diff 同时活在上下文里,同一个 `file:line` 指向两个不同的东西,agent 极易串位。而「会话记忆」本来也不可靠 —— codex 的 auto-compact 随时会把它摘掉。既然记忆迟早要靠自己重述,不如从一开始就重述得准一点:我们注入的是筛选过的结论(哪条待确认、哪条被剔除及其理由、讨论说到哪),质量高于原始上下文。

代价是旧 discussion 的追问不再有会话记忆兜底,故追问 prompt 会把该线程最近几条往来一并重述 —— 这同时也修好了 compact 之后追问的老问题。

## 全量重扫,但点明重点

重跑重新拉**最新的完整 diff** 整份重审,而不是只审增量。增量更省 token,却会漏掉老代码里上一轮没扫出来的问题 —— 而「上一轮漏了」恰恰是重跑的动机之一。作为折中,prompt 里点明 head 变化与**自上一轮以来改动过的文件**(按文件 diff 指纹比对,不是只看文件名列表),让 agent 知道重点在哪,但不裁掉它的视野。

## agent 必须对上一轮的 findings 表态

复审 prompt 列出所有**保留中**的 finding,要求逐条调用 MCP `resolve_finding`。这是重跑最大的价值点:reviewer 最想知道的是「我上轮提的问题改了没」,而不是再拿到一份重复列表。`report_finding` 的语义随之收窄为**只报新问题**。

状态有三个,`wont_fix` 不可省:

| status | 含义 |
| --- | --- |
| `fixed` | 已在最新代码中修复 |
| `wont_fix` | **作者已在 PR 上回应说明不改**(即使代码原样未变) |
| `still_present` | 代码未修复,且作者没有给出不改的理由 |

判定顺序刻意把「作者在 thread 里怎么说」排在「代码变没变」之前:①作者若说明了为何不改,选 `wont_fix` 并摘录原话;②thread 标了「已 resolve」但没留文字 —— 强信号,但仍要回代码核实;③其余按最新代码判定。

> **这一条是踩过坑补的,也是一条通用的排查顺序。** 早期只有两格,指令也只说「先到最新代码里核实」。作者在 PR 上回了「纯联调,手动调试脚本,可忽略」之后代码确实原样未变,agent 只能答 `still_present` —— 它没答错,是**我们问错了问题**:词汇表里没有「作者已回应」这一格,指令也从没要求它读作者的回复(thread 回复其实一直都注入到了 prompt 里)。**agent 给出「技术上正确但没用」的答案时,排查顺序应是 词汇 → 指令 → 数据,而不是反过来先怀疑数据没送到。**

### `fixed` 自动结案,`wont_fix` 不

`fixed` 一落库就把该条 triage 置为 `dismiss`(理由记作复核判定),同一条 SQL 完成,不经用户确认 —— 代码里已经没有的问题不该继续占着待提交清单,让 reviewer 把 agent 刚确认修好的东西再逐条手点一遍纯属体力活。结案的条目下一轮也不再进「待表态」区。

`wont_fix` 则**不**自动剔除。两者看着像,语义差得远:`fixed` 是「问题没了」,`wont_fix` 是「作者说不改」—— 后者接不接受始终是 reviewer 的决定,作者一句「可忽略」不该自动关掉一条真实的安全问题。卡上给一键采纳,把作者原话存为剔除理由。

**Duetlens 不去 resolve GitHub 上的 review thread** —— 自动结案只作用于我方 finding 的 triage,PR 上的 thread 该不该 resolve 是 **PR author 的动作**,我们不代劳。别再提「顺带同步 resolve thread」。

## 被剔除的不再出现

两层防线:

1. **软约束(prompt)**:已剔除的条目连同 reviewer 填的理由一起列出,明确要求不要重报、也不要报同类。理由是关键 —— 它让 agent 理解的是取舍标准,而不只是一个黑名单条目。
2. **硬约束(去重兜底)**:对每条新上报做匹配(同文件 + 行号邻近 + 标题相似度)。命中 **reviewer 剔除**项 → 抑制、不落库,只累加抑制计数;命中**保留中**项 → 等价于表态「仍存在」,更新 `lastSeenRound` 而不新建。判定刻意保守 —— 宁可漏判成新 finding 让用户多看一条,也不能吞掉真正的新问题。

**自动结案的条目不进黑名单**。它代表的是「当前代码里没有了」,不是 reviewer 的判断 —— 若同一处又被报出来,那是**回归**:恢复为保留态并计入本轮。prompt 里两类因此分节交代、措辞相反(reviewer 剔除的连同类都别报;已结案的再出现要当新问题报回来)。混在一节讲,等于教 agent 把回归也一并咽掉。

## GitHub 上的协作上下文

`github-pr` source 的重跑用**一条 GraphQL** 取回:

- **我方 finding 所在 thread 的后续回复** —— 按 `path` + 行号邻近 + 首条评论作者是当前 gh 身份匹配回具体 finding,连同 `isResolved` / `isOutdated` 一并挂上,并标出哪条来自 PR 作者本人(判定 `wont_fix` 只认作者的说明,旁人附和不算)。窗口内有多条候选时按标题取最像的一条 —— 只按行距取第一个的话,同文件相邻十几行的两条 finding 会把回复挂错。
- **PR 作者的 PR 级评论**、**其他 reviewer 的表态与讨论**、**PR 描述的最新版本**(用于 Scope 类审查:body 承诺了但 diff 没实现)。

除我方 thread(始终给完整往来)外,其余按时间窗过滤:**首次复审全取**整个 PR 的历史(首轮扫描不注入任何 PR 内容,此时还没有任何东西被展示过);**第三轮起**才按「上一轮开始之后」增量。

> **安全边界**:这些内容来自 PR,**任何人都能写**。统一包在带隔离前言的区块里,显式声明是外部参考材料、不是给 agent 的指令。拉取失败一律降级为空上下文而非抛错 —— gh 掉线不该让整轮复审跑不起来。

## 轮次口径

**`resolution` 只在「表态轮次 === 当前轮次」时代表本轮结论。** 第 2 轮判 `still_present` 的条目,到第 3 轮若 agent 没再表态,就该回到「未表态」,而不是一直挂着旧结论。

**唯一的例外是自动结案的 `fixed`**:结案条目按约定后续轮次不再被要求表态,`lastSeenRound` 就停在结案那轮;若也按本轮口径算,它下一轮会掉回主列表、顶着删除线冒充待处理项。判据用落库的 `autoClosed` 字段,**不是**「剔除 + fixed」—— 因为「↩ 恢复」只清 triage 与 `autoClosed`,`resolution` 照旧留着。

> 这条例外**以「仍是剔除态」为前提**。凡是拿 `resolution` 派生列表归属的地方,**先对齐 `isSubmittable` 的口径** —— 两边不一致 = 界面显示与实际提交集合对不上。同一条口径写在代码注释与本节两处,改一处必查另一处。

`dismissReason` 是**事后可选补充**,不是剔除时的必填门槛 —— 一键剔除的速度不能被输入框拖慢,但填了理由下一轮的同类抑制会准得多。

## 一轮失败:留证 + 原地重试

**失败原因必须落库。** 它在 agent 侧只存在一瞬(`turn/completed` 的 `turn.error`),编排层不接住就永久丢失 —— 用户只剩状态栏一句「失败」,重启后连这句都没有出处。

- **归因是 provider 中立的**,不直接暴露 codex 的错误码 —— 处置建议按「用户能做什么」分档(等额度 / 换模型 / 查网络 / 重新登录 / 稍后重试),而不是按某家 agent 的错误分类分档。未知一律归 `other`,不按 message 猜。
- **不做 Duetlens 自己的自动重试** —— codex 内部已退避重试若干次,再兜一层只会让失败更慢、更难解释。但 agent 重试期间要**可见**,否则那几十秒是纯黑盒。
- **重试沿用同一轮号**,不新开一轮:失败那次没有任何产出,再给它一个轮号只会让「第 N 轮」退化成重试计数。代价是失败那次的记录被覆盖,这是有意的取舍。
- **变更文件基线因此必须落在轮次行上**:失败那一轮已经把最新 diff 覆盖进快照,重试时再比一次只会得出「无改动」,复审 prompt 就会睁眼说瞎话。重试取并集。
- **开跑前失败不进轮次记录**(轮次压根没开始),就地反馈给发起处,见 [ui](ui.md#一轮机审失败归进度条不归状态栏)。

## UI 要点

- **重跑面板**摊开「这一轮会带上什么」(保留 N 条待表态 / 剔除 M 条不再报 / 已结案 K 条不再表态 / 最新 diff / PR 评论),可填本轮说明与本轮强度。面板只统计**本地已有数据** —— 最新 diff 与 PR 评论是开跑那一刻才拉的,提前拉一次既慢又会与真正开跑时的结果不一致,所以文案只说「将拉取」,不给假数字。
- **两个折叠区**:已有结论的条目移出主列表,留在原位只会淹没真正待处理的意见。「复核判定已修复」默认收起;「作者已回应,未改动」**默认展开**,因为它还等着 reviewer 决定接不接受。
- 自动结案的内联卡用「已修复 · 自动剔除」字样与 add 色(而非剔除态的 ✕ 与删除线)—— 同为剔除态,但别让人以为是自己剔的。
- **复核说明会被提交出去**:判定 `still_present` 的条目提交 / 导出时以本轮复核说明作正文主体,上一轮已提交的还会追发一条复核评论,见 [findings-submit](findings-submit.md)。
