# UI 决策

> 返回 [文档索引](../README.md)
>
> 只记**锚点决策**:为什么这么排、哪些约束不能破、哪些方向已被否决。具体视觉与交互以 `src/renderer/` 为准,实现约束写在源码注释里。tokens 与配色规则见 [design-system](design-system.md)。

## 全局

- **diff review 是主场** —— 用户交互最多的界面,三栏:文件树 / diff 主区 / 右侧 discussion 或 finding 详情。交互重心从 1.0 的「看 finding」转为「**在 diff 上对话**」。
- **duet 双声道**:两套色语言贯穿全局区分说话方 —— **agent = 天蓝**、**human = 琥珀**,作用于 gutter 锚点、卡片、头像、文件树徽标。这是 Duetlens 的记忆点,也让「谁发起的」一眼可辨。
- **明暗模式与配色主题是两个正交轴**:`data-mode`(light / dark,品牌外壳的明暗,**必须做双模式**)× `data-theme`(Duetlens / GitHub,**一整套 code-review 表面配色**,不止语法)。理由是开发者对配色有既有偏好(不少人惯用 GitHub),不该绑死在品牌色上;配色主题跟随明暗自动切子模式,用户不单独锁定。**高频的明暗留在外壳(rail 底部),低频的配色只在设置屏改**。明暗**偏好**比 `data-mode` 多一档「跟随系统」:它在渲染层解析成 light / dark 再落到属性上,tokens 与主题永远只面对两档;rail 那颗钮按 浅色 ▸ 深色 ▸ 跟随系统 轮换,不为第三档另加控件。
- 字体 **IBM Plex Sans + Mono**(工程感,去手写体 / 衬线,避开通用 AI 味);wordmark 为 mono 小写 `duetlens_` 含闪烁光标。

## 应用外壳

review 屏原先把品牌、来源、模型、用量、状态、CTA、主题、快捷键全塞进一条顶栏,既拥挤又**没有任何回到入口 / 进设置的出口**。拆成三处:

- **全局导航 rail**(左侧 52px,除 onboarding 外各屏共用):入口 · 当前审核 · 历史 · 审核规则 ▸ 明暗 · 设置。**放在顶栏之下而非贯通全高** —— 让 macOS 交通灯始终落在顶栏的 `padding-left` 里,不与 rail 抢位。
- **顶栏只留上下文**:来源 chip(github 来源整枚即打开 PR 的按钮)+ 标题 + 仓库尾注 + 右端常驻 CTA。
- **底部状态栏**(仅 review 屏):状态胶囊 · codex / 模型 / effort · ctx 环 + token · 最近工具调用 ‖ ⌘ 快捷键。
- Unified / Split 从 per-file header 迁到**中栏列头** —— 它本就是全局偏好,过去在每个文件头重复渲染一份;放状态栏则太靠边,列头紧贴它作用的那一栏。

## 主入口 / launcher

- **全屏落地屏**(非命令面板),一屏三块:wordmark hero → 发起审核卡片 → 最近的审核。会话历史直接进首页、点行恢复,不单独开页。
- 发起卡片:顶部来源 segmented,下方是共享的「附加上下文 + 单一「开始审核」CTA」。各源的列表项**点击 = 选中**,由底部唯一 CTA 发起。
- **GitHub 为主路径**:大输入框粘贴 PR 链接,**粘贴即解析**出预览卡。「从 open PR 中选择」**默认折叠**、展开才拉 —— 粘完整链接的主路径不该被列表挤走 CTA。
- **本地仓库只有一个入口,审核方式由仓库自己决定**:普通 git 分支与 GitButler 虚拟分支合成一档,因为**两者的第一步是同一个动作** —— 选同一个本地仓库;让人先在 segmented 上二选一,等于要求他记住那个仓库此刻是什么状态。选定目录后一次探测定模式:`symbolic-ref --short HEAD` 是否 `gitbutler/workspace`(**主判据 —— 不依赖 `but`、毫秒级、detached 自然落 local**),命中才跑 `but status` 作可用性副判据。
  - **入口的两档 ≠ source 层的三种实现**:`SourceKind` 仍是三值 —— 一次审核记的是**实际用了哪条 Source 实现**,历史 badge / 筛选 / 导出全靠它;收敛的只是「用户怎么选到它」。
  - **模式可见且可退**:workspace 仓库给一条低调的「改按普通 git 分支审核」链接 —— workspace 里仍有正常 ref(比如复审一个已合并的分支),纯自动会把这条路堵死;`but` 缺失或未 setup 时同样落到普通分支视图,并说明原因。
- **分支是下拉,不是卡片列表**:平铺成卡片时没人看得出「要点选」,而且没有默认值时底部 CTA 一直是灰的,像是流程卡住了。**进面板即有默认选中**,收起后由一行摘要补回被收进去的信息,展开带筛选框以应付分支多的仓库。**候选必须与「它是为哪个 repo/base 拉的」绑定** —— 否则切仓库那一帧会从上一个仓库的列表里自动选一个并重新点亮 CTA。
- **入口卡片上的计量必须与进屏后的改动面同源**:一律问 `GitButlerSource.getDiff` 走的那条路径(缺省 base 即 `but diff <branch>`),两个数由构造相等。**别再走「按 `commits[].changes` 求并集」那条弯路** —— 它的语义是「历史上触达过哪些文件」,add-then-delete 的分支会报 1 而实际 diff 是 0。
- **对比 base 是一等选项,不是高级设置**:叠在一起的分支(GitButler stack / stacked PR)下,「审哪一条」与「相对谁审」是两个自由度 —— 只给前者就只能审最上面那一层。故 base 与「审核分支」同构地并排一行,复用同一个下拉组件。
  - **默认必须是该 source 天然的那条**,且落库时存空值而非探测结果的字面量(理由见 [data-model](data-model.md))。GitButler 那档的天然基线是 **stack 里紧邻的下层分支** —— `but diff <branch>` 给的就是这条分支自己的提交,不是相对 main;这一点与直觉相反,措辞上要说出来。
  - **候选行要给的是范围而非 ref 名**:`feat/x` 本身不告诉你选它会不会把下面那个 PR 也算进来,故每行右侧标「只审这一层 / 含 N 条分支」,下方再画一条 stack 链路条把覆盖区间点亮。**链路条不换行、横向滚动** —— 深 stack 配长分支名一换行,连接线就断在半空,断线比不画更误导。
  - **跨 stack 的分支不互为 base**:不同 lane 之间没有叠加关系,拿另一条 lane 的分支当基线只会得出一份两边改动混在一起的 diff。换分支后旧 base 落不进新候选就回退到默认。
  - **切 base 即重算改动面**,且**重算走的是 source 自己那条 diff 路径**(见下一条的同源要求),不另写一条 git 命令。
- **仓库记忆**:预填上次用过的路径,空态列出最近几个仓库直接点选 —— 统一之后选目录成了本地来源的必经第一步,每次重开都从空路径开始最吵。
- **错误分级**:硬错(gh 未登录 / PR 解析失败)禁用 CTA;软警告(本地路径 remote 与 PR 不符)放行。

## 等待与进度:overlay 的分界线是「review 屏是否已存在」

- **进屏之前**用阻断浮层:此时 review 记录还没建、review 屏无从渲染,按钮上一句「启动中…」撑不住大 PR 拉 diff 的几十秒。阶段来自后端真实回调(连接来源 → 拉 diff → 建记录 → 启会话),不是定时器编的假进度。**升起前有静默期、露面后有最短停留** —— 本地分支常几百毫秒返回,闪一下比不闪更吵。**故意不给取消**:取消要么留下半张记录,要么放任 `gh` 在后台跑完。
- **重跑是这条分界线上的例外**:面板已经是用户自己打开的模态,开跑后原地转等待画面(同一套阶段与计时,只是步骤文案换成复审口径),不再另起一层浮层。重跑同样要拉最新 diff、读 PR 评论,大 PR 一样是几十秒;不同的是失败退回表单而不是转错误态 —— 说明与强度都还在,改一句就能重开。
- **进屏之后一律内联**,不用打断心智的 overlay:那时 diff 可读、可提问,盖住就是纯损失。机审进度是横跨三栏的 `.scanbar` —— 进度是**全局运行态**,不属于 Findings,曾经占掉一个 tab 的位置是错的。扫描期左侧 diff 全程可读、可点 finding、可框选提问。
- 扫描期零 finding 用镜片扫描动画占位(与启动浮层共享同一组件):这一屏空得最久,一行短提示既撑不住等待,又容易被读成「干净通过」的结论 —— 后者是扫描**结束**后零 finding 才给的正向空态,两者必须长得不一样。
- **等待期要报的是动作,不是意图**:阶段 stepper 在「通读改动」那一档要停几分钟(实测首条 finding 中位 169s、p90 302s),期间 findings 计数恒为 0,只有阶段名与转圈 —— 这段时间里唯一在变的信息是 agent 的动作(读哪个文件、搜什么、上报了什么)。故进度条常驻一行实时播报,展开区与右栏空态给可回看的动作流。**不报「它在想什么」** —— 推理摘要能开出来,但已决定不开(英文、且不抵 token 代价),见 [codex-integration](codex-integration.md#能观测到什么不能观测到什么)。
- **一行播报必须带「本步已耗时」**:实测每轮机审的最长静默中位 30s、p90 167s,没有这个数,静默期与卡死在界面上长得一模一样。动作已收尾(agent 在两步之间自己想)与这一步跑得久是两回事,措辞要分开,把在跑的动作说成「思考中」就是报假状态。
- **量化只给「改动文件已取证 N/M」,且只配一根细条**:agent 的探索长度不可预告,真百分比没有诚实的分母。这个数是**覆盖面不是完成度** —— 它跑满也不代表扫描结束(agent 还会读改动之外的上下文),文案与 title 都必须这么说,不能做成主进度。
- **展开区两栏**:左阶段时间线 │ 右侧二选一 —— 跑着讲「在做什么」,断了讲「为什么断」。失败后没有正在进行的动作可报,把动作流留在那儿只会挤掉原因与重试。
- **动作流最新一条在最上**:正序更像叙事,但要求容器一直跟着滚到底,而它的两处宿主(可收起的进度条展开区、可能不在前台的右栏)都会处于隐藏态 —— 隐藏容器几何量为 0、scroll 不派发,自动跟随会**静默失效**,恰好在事后展开来看时最不该失效。倒序没有这个失败模式。
- **展示历史有上限,累计覆盖没有**:两者合在一个数组里的话,列表一截断覆盖数就会**倒退**(已取证的文件重新变成未取证)。覆盖走独立的路径集合。
- **扫完落到哪个状态由 source 决定**:`github-pr` 还剩「提交 review 到 PR」这一步真正的终点动作,停在 `reviewing` 是有意义的待办;本地 / vbranch 没有这一步,**扫完即 `completed` 终态**,否则这类 review 永远闭不了环。追问、编辑、triage 都不改状态,只有重跑把它拉回扫描中。

## 一轮机审失败:归进度条,不归状态栏

失败是**轮次**的属性,不是一枚全局状态字。状态栏只放得下一枚状态字,把原因塞那儿等于没有原因;`.scanbar` 是唯一横跨三栏、能同时承载「断在哪一步 / 为什么断 / 怎么重试」的位置。

- **进度条失败后不卸载**,转红留在原位、stepper 停在断点;展开区从「扫描期能做什么」换成失败卡(结论 → 处置建议 → 「本轮没有产出,此前各轮的结论与你的处置都还在」→ agent 原文 → 重试)。翻进失败态强制展开 —— 原因藏在收起的横条里等于没写。
- **文案按归因分档**,可重试的那几档「重试」才是主按钮 —— 明知重试无用还把它做成主按钮,是在骗用户按。原文一律另行原样呈现,不改写、不吞证据。
- **状态栏胶囊降为指路牌**:可点、带一句结论,点了让失败卡展开并闪一下。
- **agent 内部重试要可见**:codex 自己会退避重试若干次,这几十秒原本是纯黑盒,故给一枚「连接中断,agent 重试中」。
- **「开跑前就失败」是另一类**:source 拉不到 / gh 掉线 / 仓库被移走时 agent 根本没被叫起来,没有归因可落库,只有底层命令原文。走独立的 `LaunchError`,**重跑面板与失败卡共用同一份**(两处各写各的必然漂移)。认得出的特征串给人话结论(最常见的是 vbranch 被合掉后 `but diff` 报 `No ID found for entity`),认不出就只给通用结论 + 原文。

## review 右栏三 tab

- **Discussion**:当前线程的对话,含 composer。agent 的回答带一键复制,复制的是 **markdown 原文**而非渲染后的富文本 —— 贴回编辑器 / PR 评论要的是源码;reviewer 自己写的不给复制,原文就在手边。
  - **讨论不强制锚定代码**:问架构、问整体取舍、问「这个 PR 到底想解决什么」都是真实需求,逼用户先在 diff 上框一段代码充数是错的。列表顶部的 `＋ 新讨论` 与空态下直接开打(第一句话即建线程)是同一个动作的两个入口。
  - 无锚点讨论**不能提升为 finding**:finding 提交时要落成 GitHub inline 评论,必须有行锚点。这条守卫在 store 层,UI 只是不展示按钮。
- **Findings**:运行时 triage 列表,按严重度分组(可切按文件)+ tally。**文件整个不在改动内的 finding 抽成末尾专组**,使列表顺序贴合它们在 diff 底部的物理位置,逐条点下去不再在改动处与底部之间来回弹。
- **Summary**:结论卡(codex 建议的 review event,标注「仅建议」)+ 统计条 + codex 生成的总结正文 + 重点关注文件 + 关注主题(按 category 聚合,点击筛 findings)+ 提交 / 导出入口。**整屏只读** —— 这是 agent 给 reviewer 的判断材料,不是 reviewer 的产出;要发给作者的话在提交屏自己写(见 [data-model](data-model.md))。
  - **重点关注文件**答的是 findings 答不了的那一问:哪些改动**没能变成 finding、却仍需人眼过一遍**(时序要靠人推、影响面要靠部署知识判断、需实机验证)。关注主题按 category 聚合的是**已报出的问题**,天然覆盖不到这一类,故不能靠它顶替;也不能由 app 按 findings 密度机械派生 —— 那样排出来的恰恰只有 agent 已经看懂的地方。
  - 允许锚在 diff 之外(协议本就允许 off-diff 隐患),那类置灰不可点 —— 给一个跳不过去的点击比标明「不在本次改动内」更糟。

## diff 上批注:提问与记 finding 合成一张卡

「在 diff 上说话」的核心入口。**只有一枚动作、一张卡** —— 行内 ✎ 或框选后点「段落批注」,都在锚点下方就地插入同一张 composer。

- **finding 是提问的超集,不是并列的另一件事**:卡默认只有引用块 + 正文 + `发送给 agent`;footer 的 `⚑ 记为 finding` 开关一开,就地长出 severity / category / 标题 / suggestion,正文原地变「说明」,主 CTA 换成 `新增 finding`。**升格是加法不是切换**,视线不跳,且与后端 `promoteDiscussion` 是同一条语义。升格时正文首行提为标题、降回时并回首行,两向对称一个字都不丢。
- **曾按「来路决定产物」分叉,已废**:行内 ＋ 只能发起 discussion、要记 finding 必须先框选 —— 同一个锚点因为来路不同能做的事不同,而单行记 finding 恰恰是常用场景;弹层里预先分叉也等于逼用户在打字前就下结论。
- **同轮否决的三个方案勿再提**:A「只统一入口不合窗」(最轻的单行提问从一步变两步,改主意仍要取消重来)、B「顶部两档 tab」(切换时 1 字段 ↔ 5 字段高度跳变大,还得替用户定默认档)、D「双 CTA 一次成型」(正文既当标题又当说明,需要切分规则)。
- **框选浮层保留但只剩一枚动作**:框选常常只是想复制代码,不该直接弹卡。曾有的第三个动作「◆ 追问 codex」**已删** —— 它与就地提问产出完全一致(同锚点、同一条新 user discussion、同一次首问),差别只是在哪里打字,而就地那条离代码更近。**锚定代码的新讨论因此只有中栏一条发起路径**;右栏 composer 只负责追问活跃线程,以及开一条**无锚点**的全局讨论 —— 后者中栏给不出,因为它压根不落在任何一行上。
- 行内触发点落在**新侧行号格**上,不在代码格右缘:代码格随长行横滚,贴其右缘的按钮要滑到行尾才够得着。

## diff 导航与覆盖

- **左栏两种视图随时切**:平铺(按父目录分组,组头是完整相对路径)与目录树(逐级展开 / 收拢)。默认目录树;视图是**全局偏好**,与 diff 视图同侧存 `ui_settings`,折叠状态则是 per-review 的临时态、不落库。四条取舍:①**单链目录压成一行**(`src/backend/store`)—— 左栏默认 236px,每省一级缩进就是文件名多认出几个字符;②目录行的汇总(子树文件数 + finding 徽标)**只在收起时出现**,展开态那一列数字纯属噪音,结构本身已经说清;③过滤态**强制展开命中路径但不动折叠集合**,清空过滤原样恢复;④过滤框内的 ↑/↓ 只走**可见**行,收起的分支必须真的不可达,否则会跳进看不见的文件。
  - **两种视图都不与中栏 diff 逐行同序,这是分组的固有代价,不是 bug**:平铺把后出现的文件并进先出现的同目录组,目录树进一步把同级目录排在同级文件之前(VSCode / GitHub 的文件树惯例,也是拍板时看的那版 mockup 的样子)。要逐行对齐中栏就只能不分组,而分组正是左栏存在的理由。
- **文件检索过滤只收窄树,不裁 diff**。四条易反悔的取舍:①匹配**完整路径**(`src/` 这种只写目录的词才收窄得动),空格分词逐词 AND;②每词先整段包含,**≥3 字**才退化为顺序子序列 —— 两字母词一模糊就把无关文件也捞进来,过滤等于没过滤;③**不按相关度重排** —— 顺序只由文件在 diff 中的出现次序决定,过滤前后同一批文件的相对次序不变;④**中栏 diff 保持全量** —— 裁掉会让人误判改动规模,右栏计数也跟着对不上。检索词是纯导航态,不持久化、换 review 即清空。
- **⌘F 找内容,⌘⇧F 找文件**。⌘F 的范围是**全部文件的 diff 行 + 已展开的上下文**,跨文件而非只当前文件。用户拍板的取舍:浮层贴中栏右上(代价是盖住最上方那枚 sticky file-header 右侧一小块,已接受)· 命中配色独占**靛紫**档(不占用 agent 蓝 / human 琥珀 / diff 绿红任何一档语义)· 只做区分大小写与全词匹配,**不做正则** · 已展开的上下文**算在**检索范围内(代价是命中总数随展开增长,用「当前项按身份钉住」消化)。
- **per-file Viewed 与折叠是两件事**:「已看」= 标记 + 折叠 + 推进到下一个未看文件;折叠按钮只折叠、不改 viewed。两枚都带文案 —— 纯图标读不出功能:已看是**勾选框语义**(文案恒定,状态不靠文案变化表达,免得点一下按钮宽度就跳),折叠按钮反过来给的是**点下去会发生什么**。推进只在「标记已看即折叠」开启时发生:不折叠就没有视口塌陷,此时用户多半想接着读。
- **跳到代码前先展开目标文件**:折叠态下 diff 与内联卡都不在 DOM 里,滚动会静默落空。展开只展开、不动 viewed(读过的记录不该因为回头看一眼就被抹掉),也不牵连左栏树的点选。
- **off-diff findings 分两类承载**,都保留完整卡片(triage / 编辑 / 追问),避免因无处内联被忽略:①**行 off-diff**(文件在改动内、锚点行不在新侧 hunk)归入该文件区顶部;②**文件 off-diff**(agent 顺 import 读到被引用文件并在那儿提问题)无对应文件区承载,单列到 diff 主区**底部**按文件成组,并**必须挂文件锚点** —— 否则点该卡时找不到 DOM 目标,滚动静默失败。
- **同一 hunk 的 unified / split 两张表切换,内联卡共享**(不复制),因此编辑、追问、框选、行内批注在两种视图下都可用;split 的行锚点取新侧行号。

## 键盘快捷键

- **导航键一律带 `⌘` 修饰**(`⌘1/⌘2/⌘3` 切右栏、`⌘U` 切视图、`⌘F` / `⌘⇧F` 两种检索),**裸键只留 `?` 与 `Esc`**。裸键在一屏全是输入框的 review 上要么误触、要么焦点一进输入框就被迫全体让位;带修饰键后打字时照常生效。编辑与发送统一 `⌘↵`,`↵` 留给换行(多行追问常见,不让裸 `↵` 误发)。
- **重跑键位是 `⌘E`,不是助记更顺的 `⌘R`**:`⌘R` / `⌘⇧R` 归 Electron 默认菜单的 Reload / Force Reload,按下去整屏重载,占不得。也不靠加 `⌥` 绕开 —— Windows / Linux 的 AltGr 以 `ctrl+alt` 上报,国际布局下打字就会撞上;判据里直接排除 `alt`,比事后查 `getModifierState('AltGraph')` 更彻底,也顺带躲开 macOS 上 `⌥` 作为字符合成键的那一面。
- **重跑入口不止在 diff 屏**:提交完成 / 导出屏各有一颗按钮,按同一个键则先返回 diff 再弹重跑面板 —— 「提交完等作者改完再复审一轮」是常走的一步,不该逼人自己绕回顶栏。**github 的提交屏要等提交成功才给这个入口**(按钮与键位同一判据):离开即整屏卸载,写到一半的 Review 意见与 422 定位到的失效锚点都会跟着没,藏起来的按钮配一个照样生效的键位就是一条 UI 上说不通的丢草稿路径。
- **帮助层只有一份组件**,设置屏弹同一个浮层。原先手抄的「常用摘录」已漂移出三条从未实现的键位。
- **让位原则**:任何模态打开时都不抢导航键,判据必须覆盖**全部**模态。这条对组件自带的全局键位同样成立 —— 挂在自己 window 监听上的键位不接屏侧 handler,必须显式接收模态状态并让位。

## 审核规则提示词 · 三层编辑器

- **优先级 project ▸ global ▸ builtin,按节覆盖**;合并结果注入 `thread/start · baseInstructions`。每节独立取最高优先且有定义的层作为生效值 —— 比整块替换更细,能明确「哪一节被谁覆盖」。
- **可配置面 vs 锁定段,只有前者进设置页**:
  - **可配置节** = 审核**口径**(审核重点 / 严重度判定 / 忽略范围 / 输出与语气 / 项目上下文),用户随便改。
  - **锁定段** = 工具**契约**(角色与 MCP 工具流程、`report_finding` 字段协议):severity 枚举、category 规范集、`line` 锚新侧、`suggestion` 是会被逐字套用的字面补丁。这些字段由 Duetlens 机械消费,改写不是口径变化而是**功能失常**(finding 被 ingress 拒收 / 提交到 GitHub 时补丁错位)。锁定段既不可编辑,也不下发 renderer —— 设置页里根本不存在,连「有这么一段」都不暴露。判据是「这段被改写会不会导致功能失常」。
  - 锁定段**首尾夹住**用户内容:角色段在最前(身份),协议段在最末(硬契约),用户节里写了冲突口径也压不过后面的协议。
- **节分两种**:
  - **free 节**(忽略范围 / 输出与语气 / 项目上下文)= 整节一块自由文本,**整节替换**;节内追加已拍板不做。
  - **structured 节** = 字段集固定、字段名锁死,只有正文可改,且逐字段独立继承 / 覆盖。**审核重点**的字段就是 `FINDING_CATEGORIES`(由 `Record<FindingCategory,…>` 在编译期强制每类都有 builtin 要点,与 finding 分类结构性同源、不会漂移);**严重度**的字段是 `high/medium/low`(= `z.enum(SEVERITIES)`,改名即上报被拒)。
  - **解析不出任何字段的正文**(自由文本、或自造 P0/P1 分级)视为**未覆盖**,builtin 保留 —— 否则整节被换掉,agent 会照着上报无效值而 finding 静默丢失。
  - 「先判断改动属于哪类代码、只报真实问题」这类总则不属任何类别,归锁定的角色段。
- **「继承自 X」是独立来源标签,不混排进正文**:此前写成 `继承自 builtin:正文` 前缀,读起来像规则的一部分。
- provenance 三色沿用品牌语义:project(最具体)= 天蓝、global(个人)= 琥珀、builtin(基线)= 灰。
- **不设常驻的生效结果预览栏**:编辑区已是所见即所得 —— 每节要么显示本层覆盖的正文,要么显示实际继承到的正文,节头再标生效层,读一栏就够。曾经的右栏是同一份内容的第二种排版,占掉三分之一横宽却只多给一个「合并后长这样」的说法。
- structured 节的整节徽标取最具体的那个字段,故逐字段再标一次来源 —— 否则「只改了某一类 / 某一档」在整节徽标上看不出来。
- **project 层未选仓库时照样铺开各节**,只是只读:此时没有落点文件,但生效规则(global ▸ builtin)本身要能读到;选仓库的入口收成一条与已选态同形的横条,而不是一张挡住下文的空态卡。

## 尚未落地的运行时 / 异常态

追问 turn 的中断、反向审批卡、连接断(agent-down / MCP 故障 / 离线)、上下文压缩 —— 这些态**只有设计,没有实现**。设计参照是 `mockup/review-runtime.html`(`mockup/` 整体已冻结,唯独这一份仍是它们的唯一设计参照)。

呈现原则是三处**互不打断阅读**的位置:状态栏胶囊(覆盖文案与配色)· 全局横幅(仅连接级异常,分阻断 / 警告两级)· 右栏底部运行区(中断按钮 / 审批卡 / 失败重试 / 压缩进度条)。连接断时禁用追问,但 diff 阅读与 triage 不受影响。
